CURABOT+ INTEGRATED DEMO PACKAGE
================================

FILES
-----
CuraBot_ESP32_Integrated.ino  ESP32 firmware: encoder navigation + Wi-Fi HTTP API
server.js                     Existing Node/Express proxy, updated to allow RECEPTION
index.html / style.css        Dashboard with Return to Reception button
script.js                     Dashboard command handling; STOP remains enabled
package.json / package-lock   Node dependencies
.env.example                  Environment variable template (do not commit real .env)

IMPORTANT ROUTE ASSUMPTION
-------------------------
These are provisional demo routes, each straight segment = 40 cm:
  Ward A:          Forward
  Ward B:          Forward, Right 90, Forward
  Pharmacy:        Forward, Right 90, Forward, Right 90, Forward
  Emergency Room:  Forward, Left 90, Forward

The return route is generated by reversing the stored action list and inverting
its actions (forward <-> backward, right <-> left). This is only correct if the
physical demo layout matches these route definitions.

BEFORE UPLOADING
----------------
1. Keep your original navigation sketch as a separate backup.
2. Open CuraBot_ESP32_Integrated.ino in Arduino IDE.
3. Select the correct ESP32 board and port.
4. Replace YOUR_WIFI_NAME and YOUR_WIFI_PASSWORD near the top of the sketch.
5. Confirm the encoder wiring matches the verified mapping in the sketch:
     LEFT encoder  A/B -> GPIO 32/33
     RIGHT encoder A/B -> GPIO 18/19
6. Check the motor driver and battery wiring with power disconnected before
   making any wiring changes. Keep a physical battery disconnect accessible.

FIRST TEST - DO NOT SKIP
------------------------
1. Lift the robot so both wheels are clear of the floor.
2. Upload the firmware and open Serial Monitor at 115200 baud.
3. Wait for the ESP32 IP address to print.
4. Set ESP32_URL in your local .env to that IP, e.g. http://<ESP32_IP>.
5. In the package folder, run npm install (only if dependencies are not present),
   then npm start.
6. Verify GET /status via the dashboard and confirm ESP32 Online.
7. Test STOP first. Then test one short route with wheels lifted.
8. Only after direction, encoder counts, and stop behaviour are verified should
   you place the robot on the floor for low-speed route testing.

BACKEND
-------
The Node backend runs at http://localhost:3000. Its ESP32_URL must point to the
current IP printed by the ESP32. The laptop and ESP32 must be on the same LAN.

RETURN BEHAVIOUR
----------------
After a successful destination route, click RETURN TO RECEPTION. The ESP32
executes the inverse of the exact stored route. Selecting another destination
while away from reception is rejected. If a route is stopped or times out, the
robot's exact position is unknown; manually reposition it at reception and
reboot/reset before starting a new demo route.

SAFETY NOTES
------------
- The dashboard STOP is a software stop, not a certified emergency-stop circuit.
  Keep a physical battery disconnect/power switch accessible.
- Keep wheels lifted for initial tests; use low-risk open floor space later.
- L298N current/thermal limits still apply; a higher-current BMS does not increase
  the motor driver's capability.
- Calibration values are preserved from the supplied sketch but have not been
  independently re-calibrated in this integration.
- GPIO12 is an ESP32 strapping pin; if boot becomes unreliable, investigate the
  GPIO12 driver input state during reset rather than changing pins blindly.
